# LoongForge 新环境复现指南

本文档面向公司内部新环境复现。路径示例沿用 `/Users/mac/work/loong-gcc-afl`；如使用其他路径，建议设置 `ROOT=/path/to/loongforge` 运行脚本，或保持目录名不变以减少历史报告中的绝对路径差异。

## 1. 基础依赖

已验证环境为 macOS ARM64 + Homebrew。Linux 内部环境也可以复现，但需要把 AFL++、LLVM、GNU make、Python 路径按本机实际位置设置。

基础工具：

- `git`
- `python3`
- `bash`
- `gmake`
- `jq`、`rg`（用于排查和查看结果，非核心运行依赖）
- AFL++，默认路径 `/opt/homebrew/opt/afl++`
- LLVM/Clang，默认路径 `/opt/homebrew/opt/llvm`
- 可选：`uv`，用于子模块 Python 命令的环境管理

macOS 首次运行 AFL++ 前建议执行：

```bash
sudo /opt/homebrew/opt/afl++/bin/afl-system-config
```

如果内部环境中的 AFL++/LLVM 路径不同，可用环境变量覆盖：

```bash
export AFL_ROOT=/path/to/afl++
export LLVM_ROOT=/path/to/llvm
export JOBS=8
```

## 2. 解压和基本测试

```bash
tar -xzf loongforge-delivery-*.tar.gz
cd loongforge-delivery-*

./scripts/run-basic-tests.sh
```

这一步只验证 Python 代码、CLI 解析和 shell 脚本语法，不访问网络、不调用 LLM、不构建 GCC。

## 3. 拉取锁定源码

交付包不包含完整 GCC/binutils 源码。使用脚本按 `third_party/SOURCES.lock` 拉取锁定版本：

```bash
./scripts/bootstrap-sources.sh
```

默认远程：

- GCC：`https://gcc.gnu.org/git/gcc.git`
- binutils-gdb：`ssh://sourceware.org/git/binutils-gdb.git`

内部环境如果使用公司镜像：

```bash
GCC_REPO_URL=ssh://internal/git/gcc.git \
BINUTILS_REPO_URL=ssh://internal/git/binutils-gdb.git \
./scripts/bootstrap-sources.sh
```

如需使用团队自己的 GCC fork，可先保证 fork 包含锁定 commit，或将 `GCC_COMMIT` 设置为公司确认的 fork commit：

```bash
GCC_REPO_URL=ssh://internal/git/team-gcc-fork.git \
GCC_COMMIT=<team-fork-commit> \
./scripts/bootstrap-sources.sh
```

## 4. 构建普通 LoongArch64 binutils

```bash
./scripts/build-binutils.sh
```

默认安装到：

```text
install/bin/loongarch64-linux-gnu-as
install/bin/loongarch64-linux-gnu-ld
```

可覆盖目标和安装目录：

```bash
TARGET=loongarch64-linux-gnu PREFIX=/path/to/install ./scripts/build-binutils.sh
```

## 5. 构建 AFL++ 插桩 GCC

```bash
./scripts/build-gcc-afl.sh
```

默认安装到：

```text
install-afl/bin/loongarch64-linux-gnu-gcc
install-afl/bin/loongarch64-linux-gnu-g++
install-afl/libexec/gcc/loongarch64-linux-gnu/17.0.0/cc1
install-afl/libexec/gcc/loongarch64-linux-gnu/17.0.0/cc1plus
```

验证插桩、showmap 和短时 fuzz：

```bash
./scripts/verify-gcc-afl.sh
```

查看单个样例 edge map：

```bash
./scripts/afl-showmap-gcc.sh seeds/minimal.c -- -O2
```

运行短时 AFL++ 质量 fuzz：

```bash
./scripts/run-gcc-afl-fuzz.sh \
  --seconds 60 \
  --output out/ci-smoke \
  seeds -- -O2

./scripts/afl-coverage-report.sh out/ci-smoke -- -O2
```

## 6. 可选：构建 gcov 口径 GCC

如果需要回答“覆盖了多少 GCC 源码行/函数”，构建 gcov 版本：

```bash
./scripts/build-gcc-gcov.sh
```

然后用 InstanLLM covered corpus 重放：

```bash
python3 scripts/gcc-source-coverage-replay.py \
  --evaluations instan-llm/out/evaluations.jsonl \
  --prefix install-gcov \
  --out-dir out/source-coverage/instanllm-covered
```

AFL edge coverage 和 gcov 源码行/函数覆盖是不同指标：前者用于 fuzz feedback，后者用于质量汇报。

## 7. 配置 LLM provider

复制环境模板：

```bash
cp .env.example .env
```

填写：

```dotenv
DEEPSEEK_API_ENDPOINT=https://api.deepseek.com
DEEPSEEK_API_KEY=...
DEEPSEEK_MODEL=...
```

内部 provider 只要兼容 OpenAI Chat Completions 风格接口，即可通过 endpoint/model 切换。密钥只从环境变量读取，不会写入输出 JSON。

## 8. Bugzilla -> ExtractLLM -> GroupLLM -> InstanLLM

如果要从 Bugzilla 重新生成语料：

```bash
cd gcc-bugzilla-loongarch
uv run loongarch-bug-corpus sync --delay 1.0
uv run loongarch-bug-corpus verify
cd ..
```

如果只复现 LLM feature 抽取：

```bash
cd extract-llm
PYTHONPATH=src python3 -m extract_llm prepare \
  --corpus-dir ../gcc-bugzilla-loongarch \
  --output-dir out
PYTHONPATH=src python3 -m extract_llm run \
  --output-dir out \
  --keep-going
PYTHONPATH=src python3 -m extract_llm build-pool --output-dir out
cd ..
```

GroupLLM 可以直接使用交付包中的 curated snapshot，也可以重新运行：

```bash
cd group-llm
PYTHONPATH=src python3 -m group_llm prepare \
  --feature-pool ../extract-llm/out/feature-pool.jsonl \
  --append-groups 48 \
  --coverage-basis ready \
  --target-profile loongarch
PYTHONPATH=src python3 -m group_llm run --workers 4 --retries 3
PYTHONPATH=src python3 -m group_llm build-groups
cd ..
```

InstanLLM 生成并评估测试程序：

```bash
cd instan-llm
PYTHONPATH=src python3 -m instan_llm run \
  --groups-file ../group-llm/out/feature-groups.jsonl \
  --workers 2
PYTHONPATH=src python3 -m instan_llm evaluate \
  --optimization=-Ofast \
  --timeout-ms 30000
PYTHONPATH=src python3 -m instan_llm build-corpus
cd ..
```

## 9. 长程 AFL feedback 闭环

推荐先跑小批校准：

```bash
scripts/run-afl-feedback-loop.py \
  --iterations 1 \
  --batch-size 8 \
  --group-parallel 2 \
  --instan-workers 1 \
  --optimization=-Ofast
```

provider 稳定后再跑正式批：

```bash
scripts/run-afl-feedback-loop.py \
  --iterations 2 \
  --batch-size 48 \
  --group-parallel 4 \
  --group-api-timeout 300 \
  --group-process-timeout 720 \
  --group-retries 3 \
  --instan-workers 4 \
  --instan-process-timeout 720 \
  --evaluate-timeout-ms 30000 \
  --optimization=-Ofast \
  --coverage-basis ready
```

可选打开 AFL++ 原生变异阶段：

```bash
scripts/run-afl-feedback-loop.py \
  --iterations 1 \
  --batch-size 48 \
  --group-parallel 4 \
  --group-api-timeout 300 \
  --instan-workers 4 \
  --optimization=-Ofast \
  --native-afl-seconds 180 \
  --native-afl-languages c \
  --native-afl-timeout 5000+
```

如果 provider 出现大量 read timeout、空响应或 parser error，应先降低并发或更换 provider，不要把低质量批次作为效果评估依据。

## 10. ICE/crash 复核

发现 ICE-like crash 后不要直接认定为新 bug。标准流程：

1. 保存 generated source、compiler options、stderr tail、AFL map 和 signature hash；
2. 用相同 `cc1/cc1plus`、相同 `-Ofast` 与 target options 复现；
3. 对比 `source_bug_ids`、历史 Bugzilla PoC 和已有 stderr signature；
4. 能对应历史 PoC 的，归类为“已知问题再覆盖”；
5. 无法对应的，进入最小化和人工确认流程。
